  翻译层测试（5 项）

  测试的是中间代理（OpenRouter / Claude Bridge / Claude Adapter）在做 Anthropic↔OpenAI 格式转换时，有没有引入 Bug。

  | #   | 测试项       | 为什么测这个                                             | 背后风险                                                                                 |
  |-----|-----------|----------------------------------------------------|--------------------------------------------------------------------------------------|
  | 1   | 基本对话      | 最基础的能力：能否发请求、收响应                                   | 翻译层可能完全不工作（路由、认证出错）                                                                  |
  | 2   | 流式对话      | SSE 流式是实时对话的核心                                     | 翻译层可能只转发了 HTTP 但没正确转发流（Claude Bridge 就挂在这）                                           |
  | 3   | 工具调用（非流式） | 翻译层能否把 Anthropic 的 tools 参数正确转成 OpenAI 的 functions | OpenAI 和 Anthropic 的 tool 格式不一样，翻译错就调不了工具                                            |
  | 4   | 工具结果回传    | 多轮对话中 ID 映射是否正确                                    | Anthropic ID 是 toolu_xxx，OpenAI 是 call_xxx。翻译层必须记住映射，否则第二轮报错 400（Claude Bridge 就挂在这） |
  | 5   | 流式工具调用    | 流式中 tool 参数是增量传输的，翻译层能否正确拼接                        | Anthropic 的 input_json_delta → OpenAI 的 function.arguments，增量流式翻译是最容易丢数据的（社区工具的通病）   |

  总结：这 5 项覆盖了翻译层的所有关键路径——请求/响应格式、流式传输、工具参数翻译、ID 映射、增量数据完整性。一项不过，翻译层就不能用于生产。

  模型准确性测试（6 项）

  测试的是GPT 模型本身能否正确使用 SDK 的实际工具 Schema。翻译层通过后，还要确认模型不会传错参数。

  | #   | 测试项            | 为什么选这个工具                | 核心检查点                                                                       |
  |-----|----------------|-------------------------|-----------------------------------------------------------------------------|
  | 1   | Read pages 参数  | 生产中发现 GPT 传了 pages=""   | 空字符串 vs 合法格式 "3-8"                                                          |
  | 2   | Grep 多参数组合     | Grep 有 15 个参数，是最复杂的工具   | 参数类型（-i 应为 boolean 而非 string）、枚举值（output_mode 只能是 3 种）、边界（head_limit 应为正整数） |
  | 3   | Edit 必填参数完整性   | Edit 要求 3 个必填参数         | 模型是否漏传必填参数、new_string 是否和 old_string 不同                                     |
  | 4   | Bash 参数类型      | timeout 单位、boolean 类型参数 | timeout 不能传字符串、"30000"不是数字、run_in_background 应为 boolean                     |
  | 5   | WebSearch 数组参数 | 需要传数组类型                 | 模型能否正确构造 allowed_domains: ["github.com"] 而非字符串                              |
  | 6   | Read 不带可选参数    | 检查模型是否"发明"不存在的参数        | 读 /etc/hosts 时不应该传 pages 或 offset                                           |

  总结：这 6 项覆盖了 SDK 工具参数的所有类型风险——字符串 vs 数字 vs 布尔 vs 枚举 vs 数组 vs undefined。测试用例直接用 SDK 的真实 Schema，不是简单的 get_weather。

  为什么拆成两个文件

  因为失败原因不同，修复方式也不同：

  翻译层测试失败     →  修翻译代理代码   →  开发者修
  准确性测试失败     →  换模型           →  只能接受或等模型更新

  翻译层失败是你能修的，准确性失败是不能修的
